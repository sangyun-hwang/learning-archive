# Monolith and Modular Monolith

## Monolith

Monolith는 하나의 애플리케이션 안에 여러 비즈니스 기능이 함께 들어 있고, 하나의 단위로 빌드되고 배포되는 구조다.

쇼핑몰 서비스를 예로 들면 다음 기능이 있을 수 있다.

```txt
회원
상품
주문
결제
배송
관리자
```

이 모든 기능이 하나의 서버 애플리케이션 안에 들어 있고 하나로 배포된다면 monolith 구조라고 볼 수 있다.

```txt
shopping-api
  user
  product
  order
  payment
  delivery
```

보통 monolith는 MSA처럼 `user-service`, `order-service`, `payment-service`로 서버를 나누지 않고, 하나의 서버가 전체 기능을 처리하는 구조를 말한다.

## Monolith의 장점

- 구조가 단순하다.
- 배포가 단순하다.
- 초기 개발 속도가 빠르다.
- 하나의 프로세스 안에서 호출하므로 통신이 단순하다.
- 하나의 DB 트랜잭션으로 처리하기 쉬운 경우가 많다.
- 작은 팀이나 초기 서비스에 적합하다.

## Monolith의 단점

- 코드가 커질수록 결합도가 높아질 수 있다.
- 한 기능의 변경이 전체 배포로 이어질 수 있다.
- 모듈 경계가 흐려지기 쉽다.
- 특정 기능만 독립적으로 확장하기 어렵다.
- 규모가 커질수록 빌드, 테스트, 유지보수가 복잡해질 수 있다.

## Modular Monolith

Modular Monolith는 배포 단위는 하나로 유지하되, 내부 코드는 도메인이나 기능별 모듈로 명확히 나누는 구조다.

```txt
shopping-api
  user
  product
  order
  payment
  delivery
```

핵심은 다음과 같다.

```txt
배포 단위는 하나
내부 구조는 모듈 단위로 분리
```

즉 Modular Monolith는 MSA처럼 서버를 물리적으로 쪼개기 전에, 하나의 애플리케이션 안에서 도메인 경계를 먼저 정리하는 방식이다.

## 단순히 폴더를 나누는 것과의 차이

폴더를 나누는 것만으로 Modular Monolith가 되지는 않는다.

모듈 경계를 지킨다는 것은 다른 모듈의 내부 구현을 직접 건드리지 않고, 공개된 API, interface, service, event 등을 통해 협력한다는 뜻이다.

예를 들어 `order` 모듈이 `payment` 모듈의 내부 DB table이나 내부 class를 마음대로 직접 수정하면 모듈 경계가 깨진다.

좋은 방향은 다음과 같다.

```txt
order -> payment의 공개 interface 호출
order -> payment event 발행
order -> payment 내부 구현 직접 접근 X
```

이렇게 해야 내부는 하나의 애플리케이션이지만, 각 모듈의 책임과 경계를 유지할 수 있다.

## MSA와의 차이

| 구분 | Modular Monolith | MSA |
| --- | --- | --- |
| 배포 단위 | 하나 | 여러 서비스 |
| 프로세스 | 하나인 경우가 많음 | 서비스별 분리 |
| 통신 | 내부 호출 | 네트워크 호출 |
| 트랜잭션 | 상대적으로 단순 | 분산 트랜잭션 고려 |
| 운영 복잡도 | 낮은 편 | 높은 편 |
| 모듈 경계 | 코드 구조와 규칙으로 관리 | 서비스 분리로 강제 |

Modular Monolith는 MSA보다 운영 복잡도가 낮지만, 모듈 경계를 코드 규칙과 설계로 지켜야 한다.

## Frontend FSD와의 관계

프론트엔드에서도 하나의 앱 안에 여러 도메인과 기능이 들어간다.

FSD는 프론트엔드 코드베이스 안에서 관심사와 도메인 경계를 나누는 구조화 방법이다.

Modular Monolith와 FSD는 모두 “하나의 코드베이스 안에서 경계를 나눈다”는 점이 닮았다.

다만 용어의 초점은 다르다.

```txt
Monolith / Modular Monolith:
주로 백엔드 애플리케이션의 배포 구조와 도메인 모듈 경계를 설명한다.

FSD:
프론트엔드 코드베이스 안에서 관심사와 도메인 경계를 나누는 구조화 방법이다.
```

즉 프론트엔드의 FSD 감각은 Modular Monolith의 사고방식과 비슷하지만, Monolith라는 용어는 보통 백엔드 서버 아키텍처에서 더 많이 사용된다.

## 언제 적합한가?

Modular Monolith는 다음 상황에 적합하다.

- 서비스 규모가 아직 크지 않다.
- 팀이 작고 운영 복잡도를 낮게 유지하고 싶다.
- 도메인 경계를 정리하고 싶지만 MSA까지는 필요하지 않다.
- 하나의 배포 단위로 빠르게 개발하고 싶다.
- 나중에 필요한 모듈만 분리할 가능성을 열어두고 싶다.

## 정리

Monolith는 여러 비즈니스 기능이 하나의 애플리케이션으로 빌드되고 배포되는 구조다.

Modular Monolith는 하나로 배포하되 내부를 도메인 모듈로 나누고, 모듈 간 경계를 지키는 구조다.

핵심은 MSA처럼 무조건 서버를 나누는 것이 아니라, 먼저 하나의 애플리케이션 안에서 책임과 경계를 명확히 하는 것이다.
