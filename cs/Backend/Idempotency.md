# Idempotency

## 개념

Idempotency, 멱등성은 같은 요청을 여러 번 수행해도 서버의 최종 상태가 한 번 수행했을 때와 같게 유지되는 성질이다.

중요한 점은 응답 코드가 항상 같아야 한다는 뜻이 아니라, 요청이 서버 상태에 미치는 최종 효과가 같아야 한다는 것이다.

예를 들어 같은 게시글 삭제 요청을 두 번 보냈을 때 첫 번째 요청은 `204 No Content`, 두 번째 요청은 `404 Not Found`를 반환할 수 있다.

```txt
DELETE /posts/1
DELETE /posts/1
```

응답은 다를 수 있지만 최종 상태는 동일하다.

```txt
posts/1은 존재하지 않는다.
```

따라서 `DELETE`는 멱등적인 메서드로 볼 수 있다.

## 요청 메서드별 멱등성

| Method | 멱등성 | 설명 |
| --- | --- | --- |
| `GET` | 멱등적 | 조회 요청이므로 여러 번 호출해도 리소스 상태를 바꾸지 않는다. |
| `HEAD` | 멱등적 | body 없이 metadata만 조회한다. |
| `OPTIONS` | 멱등적 | 서버가 지원하는 메서드나 통신 옵션을 확인한다. |
| `PUT` | 멱등적 | 특정 리소스를 요청 body의 상태로 교체한다. 같은 body를 반복하면 최종 상태가 같다. |
| `DELETE` | 멱등적 | 같은 리소스를 여러 번 삭제해도 최종 상태는 리소스가 없는 상태다. |
| `POST` | 기본적으로 비멱등 | 호출할 때마다 새 리소스 생성, 주문, 결제 같은 새로운 결과가 생길 수 있다. |
| `PATCH` | 설계에 따라 다름 | `count += 1`처럼 누적 변경이면 비멱등, `name = "kim"`처럼 값 지정이면 멱등적으로 만들 수 있다. |

## PUT과 POST의 차이

`PUT`은 보통 특정 리소스를 지정한 상태로 교체할 때 사용한다.

```http
PUT /users/1
Content-Type: application/json

{
  "name": "Kim"
}
```

같은 요청을 여러 번 보내도 `/users/1`의 최종 상태는 같다.

반면 `POST`는 보통 새 리소스를 생성할 때 사용한다.

```http
POST /users
Content-Type: application/json

{
  "name": "Kim"
}
```

같은 body를 여러 번 보내도 새로운 user가 여러 개 생성될 수 있다. id, 생성 시간, 주문 번호처럼 요청마다 달라지는 값이 생기므로 기본적으로 비멱등적이다.

## PATCH와 멱등성

`PATCH`는 부분 수정 요청이므로 어떤 방식으로 수정하느냐에 따라 멱등성이 달라진다.

비멱등 예시:

```http
PATCH /counter
Content-Type: application/json

{
  "operation": "increment",
  "value": 1
}
```

이 요청은 호출할 때마다 `count`가 1씩 증가한다. 한 번 호출한 결과와 여러 번 호출한 결과가 다르므로 비멱등적이다.

멱등 예시:

```http
PATCH /users/1
Content-Type: application/json

{
  "name": "Kim"
}
```

이 요청은 여러 번 보내도 `name`이 `"Kim"`인 상태로 유지된다. 이런 경우는 멱등적으로 설계할 수 있다.

## Idempotency-Key

결제나 주문 같은 작업은 `POST`로 처리되는 경우가 많지만, 재시도에 안전해야 한다.

예를 들어 결제 요청 중 네트워크 연결이 끊기면 클라이언트는 결제가 성공했는지 실패했는지 확실히 알 수 없다. 이때 같은 요청을 재시도했는데 서버가 새 결제로 처리하면 중복 결제가 발생할 수 있다.

이를 막기 위해 `Idempotency-Key`를 사용한다.

```http
POST /payments
Idempotency-Key: order-123-payment-1
Content-Type: application/json

{
  "orderId": "order-123",
  "amount": 30000
}
```

서버는 key를 기준으로 요청 처리 상태와 결과를 저장한다.

```txt
처음 보는 key
-> 요청 처리
-> 처리 결과 저장
-> 결과 반환

이미 처리한 key
-> 다시 처리하지 않음
-> 저장된 결과 반환
```

저장해야 하는 정보는 보통 다음과 같다.

- idempotency key
- 요청을 보낸 사용자 또는 계정
- 요청 fingerprint 또는 body hash
- 처리 상태
- 처리 결과 또는 응답
- 만료 시간

단순히 “같은 내용이면 중복으로 본다”가 아니라, 클라이언트가 명시한 key와 서버의 처리 기록을 기준으로 중복 처리를 막는다.

## 주의할 점

`Idempotency-Key`는 debounce와 다르다.

debounce는 짧은 시간 안에 연속된 이벤트를 하나로 줄이는 클라이언트 UI 패턴이다. 반면 idempotency는 네트워크 재시도, 서버 처리 완료 후 응답 실패, 중복 요청 같은 상황에서도 서버가 같은 작업을 두 번 처리하지 않도록 하는 API 설계다.

또한 같은 key로 다른 요청 body가 들어오면 서버는 충돌로 보고 거부해야 한다. 그렇지 않으면 같은 key가 다른 의미의 요청에 재사용될 수 있다.

## 정리

멱등성은 같은 요청을 여러 번 보내도 서버의 최종 상태가 한 번 보낸 것과 같게 유지되는 성질이다.

조회 요청은 보통 자연스럽게 멱등적이지만, 결제나 주문처럼 상태를 변경하는 요청은 재시도와 중복 요청을 고려해야 한다.

`Idempotency-Key`는 비멱등적인 `POST` 요청을 재시도에 안전하게 만들기 위한 대표적인 방법이다.
