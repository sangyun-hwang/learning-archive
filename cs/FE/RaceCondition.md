# Race Condition: 공유 상태의 경쟁과 비동기 응답 순서

## 개념

Race Condition(경쟁 상태)은 여러 작업이 공유 상태를 사용하거나 변경할 때 실행·완료 순서에 따라 올바르지 않은 결과가 생길 수 있는 문제다. 이 문서는 공유 데이터의 갱신 경쟁과 프론트엔드의 응답 순서 문제를 함께 다룬다.

## 공유 상태를 두고 경쟁하는 경우

재고가 1개인 상품을 두 요청이 동시에 구매한다고 가정한다. 서버가 재고를 읽고, 애플리케이션에서 계산한 값을 별도의 쿼리로 저장하면 다음 순서가 가능하다.

```text
초기 재고: 1

A: 재고 1 읽음 -> 구매 가능하다고 판단
B: 재고 1 읽음 -> 구매 가능하다고 판단
A: 계산한 재고 0 저장 -> 주문 성공
B: 계산한 재고 0 저장 -> 주문 성공

최종 재고는 0인데 주문은 2개 성공
```

두 요청이 같은 이전 값을 보고 각각 결과를 저장해 한쪽의 갱신 효과가 사라지는 lost update 사례다. 재고가 음수가 되지 않았다고 데이터가 올바른 것은 아니다. 검사 시점에는 유효했던 조건이 실제 변경 시점까지 유지된다고 가정한 것도 문제다.

공유 상태는 DB의 재고뿐 아니라 잔액, 예약 좌석이나 메모리의 변수일 수도 있다. 해결하려면 '읽기 -> 판단 -> 변경'에서 다른 작업이 끼어들어도 지켜야 할 조건을 보장해야 한다.

### 서버에서는 원자적 갱신과 동시성 제어

단일 상품의 재고를 1개 차감하는 예로, PostgreSQL에서는 조건 검사와 차감을 하나의 UPDATE로 수행할 수 있다.

```sql
UPDATE products
SET stock = stock - 1
WHERE id = $1 AND stock > 0
RETURNING stock;
```

반환된 행이 있는지 확인해 차감 성공 여부를 판단한다. PostgreSQL의 Read Committed에서는 같은 행을 수정하는 작업이 경합하면 대기 후 갱신된 행에 WHERE 조건을 다시 평가한다. 위 예제에서는 먼저 성공한 요청 이후 재고가 0이면 다음 요청은 차감하지 않는다. [PostgreSQL: Transaction Isolation](https://www.postgresql.org/docs/current/transaction-iso.html)

주문 생성과 재고 차감처럼 함께 성공해야 하는 변경은 트랜잭션으로 묶는다. 다만 트랜잭션으로 감쌌다는 사실만으로 모든 경쟁 상태가 해결되지는 않는다. 데이터베이스와 격리 수준, 쿼리 구성에 따라 적절한 동시성 제어가 필요하다.

| 방법 | 기본 아이디어 |
| --- | --- |
| 원자적 조건부 갱신 | 조건 확인과 변경을 하나의 연산으로 수행 |
| 비관적 잠금 | 대상 행 등을 잠근 뒤 읽고 변경 |
| 낙관적 잠금 | 읽었던 버전과 현재 버전이 같은 경우만 변경하고 충돌 처리 |

프론트엔드에서 버튼을 비활성화해도 다른 탭이나 사용자의 요청까지 막을 수는 없다. 공유 데이터의 무결성은 서버와 DB에서 보장한다. 멱등성 키는 같은 작업의 재시도 중복 처리를 줄이는 데 쓰이며, 서로 다른 사용자의 구매 경쟁까지 자동으로 해결하는 것은 아니다.

## 프론트엔드의 응답 순서 경쟁

검색 화면에서는 여러 응답이 같은 결과 state를 변경하려는 상황이 생긴다.

```text
0초: react 검색 요청 A 시작
1초: next 검색 요청 B 시작
2초: B 응답 -> next 결과 표시
3초: A 응답 -> react 결과로 덮어씀
```

사용자가 마지막으로 선택한 검색어는 next이지만 화면에는 react 결과가 남는다. 네트워크와 서버 처리 시간 때문에 요청 시작 순서와 응답 완료 순서가 다를 수 있다.

## 싱글 스레드에서도 발생하는 이유

메인 스레드의 JavaScript 코드는 한 번에 하나씩 실행되지만, 여러 비동기 요청의 진행 시간은 겹칠 수 있다. 각 응답을 처리하는 콜백이 하나씩 실행된다는 사실이 요청 시작 순서대로 완료된다는 뜻은 아니다.

이 사례는 두 코드가 같은 순간 CPU에서 실행되어야만 생기는 문제가 아니다. 뒤늦게 실행된 이전 요청의 콜백이 최신 상태를 덮어쓸 수 있다는 것이 핵심이다.

## 이전 응답 무시하기

React Effect에서는 cleanup으로 이전 실행의 결과를 더 이상 반영하지 않도록 할 수 있다. 아래는 컴포넌트 안에서 query와 상태 변경 함수를 사용하는 부분 예제다.

```jsx
useEffect(() => {
  let ignore = false;

  async function load() {
    try {
      const response = await fetch(
        `/api/search?q=${encodeURIComponent(query)}`,
      );
      if (!response.ok) throw new Error('검색 실패');
      const data = await response.json();

      if (!ignore) setResults(data);
    } catch (error) {
      if (!ignore) setError(error);
    }
  }

  load();
  return () => {
    ignore = true;
  };
}, [query]);
```

query가 바뀌어 새 Effect가 실행되기 전에 이전 Effect의 cleanup이 실행된다. 각 Effect 실행은 별도의 ignore 변수를 가지므로, 이전 요청의 결과는 무시하고 현재 실행의 결과는 반영할 수 있다. 컴포넌트가 제거될 때도 cleanup이 실행된다. [React 공식 예제](https://react.dev/reference/react/useEffect#fetching-data-with-effects)

ignore는 네트워크 요청을 취소하지 않는다. 요청과 응답 처리는 계속될 수 있지만 오래된 실행이 상태를 변경하지 않도록 막는다. 실제 화면에서는 오류 초기화와 로딩 표시도 구성하며, 이전 요청의 오류나 finally에서 최신 요청의 상태를 변경하지 않도록 같은 유효성 검사를 적용한다.

## 취소와 요청 ID 비교

| 방법 | 역할 |
| --- | --- |
| Ignore | 오래된 작업의 결과를 상태에 반영하지 않음 |
| AbortController | signal을 지원하는 작업에 취소 신호 전달 |
| 요청 ID 비교 | 현재 요청 ID와 일치하는 응답만 반영 |

AbortController로 불필요한 fetch를 취소하면 자원 사용을 줄일 수 있다. 지원하지 않는 후속 작업까지 강제로 중단시키는 것은 아니므로 필요하면 결과 반영 시 유효성 검사도 함께 사용한다. 클라이언트에서 요청을 취소해도 이미 실행된 서버 작업이 되돌아가는 것은 아니다. [MDN: AbortController](https://developer.mozilla.org/en-US/docs/Web/API/AbortController)

요청 ID 비교는 요청을 시작할 때 번호를 증가시키고 응답 시 최신 번호인지 확인하는 방식이다. React 이벤트 핸들러에서는 ref 등에 최신 번호를 유지할 수 있다.

```js
// 이벤트 핸들러 내부의 흐름 예시
const requestId = ++latestRequestId.current;
const data = await search(query);
if (requestId === latestRequestId.current) {
  setResults(data);
}
```

위 코드는 아이디어를 설명하는 부분 예제이며 오류 처리와 컴포넌트 제거 시 처리는 별도로 구성한다. '최신 요청만 반영'은 검색 같은 작업의 정책이지, 모든 작업에 적용하는 규칙은 아니다. 여러 상품을 추가하는 작업이라면 각 작업의 결과가 모두 중요할 수 있다.

## Debounce만으로 해결되지 않는 이유

Debounce는 입력이 이어지는 동안 실행을 미루어 요청 횟수를 줄인다. 이미 전송된 요청의 완료 순서를 보장하거나 자동으로 취소하지는 않는다. 따라서 요청 횟수 제어와 오래된 응답 반영 방지를 구분한다.

## 간단한 실습 방향

검색어 A의 응답은 2초, 검색어 B는 0.3초 뒤에 도착하도록 가짜 API를 구성한다. A를 요청한 뒤 B를 요청해 오래된 결과가 화면을 덮는지 확인하고, ignore나 요청 ID 비교를 추가해 결과를 비교할 수 있다. 실제 실습과 브라우저 검증은 아직 진행하지 않았다.

## 말로 설명하기

Race Condition은 여러 작업이 같은 상태를 다룰 때 처리 순서에 따라 잘못된 결과가 생기는 경쟁 상태입니다. 재고가 하나인데 두 요청이 모두 재고 하나를 읽고 주문을 성공시키는 사례가 있습니다. 서버에서는 조건부 원자적 갱신이나 잠금, 적절한 트랜잭션 처리로 데이터 조건을 지킵니다. 프론트엔드에서는 이전 검색 응답이 최신 화면을 덮어쓰는 사례가 있고, 유효한 응답만 반영하도록 처리합니다. 어떤 상태가 공유되고 어떤 조건을 지켜야 하는지에 따라 해결 방법을 선택합니다.

### 프론트엔드 사례를 더 물어보면

프론트엔드의 Race Condition은 비동기 작업의 완료 순서에 따라 화면 결과가 달라지는 문제입니다. 검색 요청을 연속으로 보냈을 때 먼저 보낸 응답이 늦게 도착해 최신 결과를 덮어쓸 수 있습니다. JavaScript는 싱글 스레드지만 네트워크 요청의 완료 순서까지 보장하지는 않습니다. 이전 결과를 무시하거나 요청 ID로 최신 응답인지 확인하고, 취소 가능한 작업에는 AbortController를 사용할 수 있습니다. Debounce는 요청 횟수를 줄이는 방법이라 응답 순서 문제는 별도로 처리해야 합니다.
