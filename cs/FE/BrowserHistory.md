# 히스토리 스택과 렌더링 방식별 뒤로·앞으로 가기

## 기록 목록과 현재 위치

브라우저의 뒤로·앞으로 가기는 방문 기록에서 현재 위치를 이동하는 기능이다. 이해를 위해 기록 목록과 현재 위치를 가리키는 포인터로 생각할 수 있다. 실제 브라우저의 세션 히스토리는 문서와 관련 상태 등도 다루지만, 여기서는 기본 이동 원리에 집중한다.

```text
A -> B -> C
          ^ 현재

뒤로 가기
A -> B -> C
     ^ 현재

앞으로 가기
A -> B -> C
          ^ 현재
```

뒤로 갈 때 기록을 삭제하지 않기 때문에 앞으로 이동할 기록도 남아 있다. 하나의 스택에서 무조건 pop한다고 이해하기보다 목록의 현재 위치를 이동한다고 이해하면 쉽다.

## 뒤로 간 뒤 새로운 이동

```text
A -> B -> C
     ^ B로 돌아온 상태

여기서 D로 새 이동
A -> B -> D
          ^ 현재
```

B 뒤의 앞으로 가기 기록 C를 버리고 D를 새 기록으로 추가한다. C의 내용을 D로 수정하는 것은 아니다. 이 상태에서 앞으로 가기로 C에 갈 수는 없다.

## 편집기 Undo / Redo와 비교

일반적인 선형 Undo / Redo도 현재 위치를 이전·다음 편집 기록으로 옮긴다. Undo 후 새 편집을 하면 기존 Redo 이력을 버리는 방식으로 구현할 수 있다.

| 구분 | 기록 대상 | 이전으로 돌아갈 때 |
| --- | --- | --- |
| 편집기 Undo / Redo | 데이터 스냅샷이나 변경 명령 | 문서·데이터 상태를 되돌림 |
| 브라우저 뒤로·앞으로 | 방문 기록과 관련 상태 | 해당 기록의 페이지로 이동 |

편집기는 과거·현재·미래 상태를 나누거나 명령과 역연산을 저장하는 방식 등으로 구현한다. 모든 편집기가 동일한 내부 구조를 쓰는 것은 아니다.

브라우저 방문 기록은 서버 데이터의 변경 이력이 아니다. 주문 완료 후 뒤로 가도 이미 백엔드가 처리한 주문은 취소되지 않는다. 취소는 별도의 서버 작업이 필요하다.

## History API

| API | 역할 |
| --- | --- |
| pushState | 현재 위치 뒤에 새 기록 추가, 기존 앞으로 가기 기록 제거 |
| replaceState | 새 기록을 추가하지 않고 현재 기록 교체 |
| back / forward / go | 기존 기록에서 현재 위치 이동 |

pushState는 같은 문서에서 기록과 URL을 변경할 수 있지만, 그 자체로 문서를 요청하거나 React 화면을 변경하지 않는다. SPA 라우터가 기록 변경과 UI 갱신을 연결한다. [MDN: History API](https://developer.mozilla.org/en-US/docs/Web/API/History_API)

뒤로·앞으로 가기로 같은 문서의 기록을 이동하면 popstate를 활용할 수 있다. pushState나 replaceState 호출 자체는 popstate를 발생시키지 않는다.

## 렌더링 방식에 따른 화면 처리

방문 기록 이동이라는 원리는 공통이다. SSR·CSR은 이동한 기록의 화면을 어떻게 준비하는지에 영향을 준다. Server Component는 별도의 히스토리 방식이 아니라 서버에서 실행되는 컴포넌트다.

| 환경 | 기록 이동에 대응하는 화면 처리 |
| --- | --- |
| 전통적인 SSR 문서 이동 | bfcache로 이전 문서 복원 또는 문서 다시 로드 |
| CSR SPA 내부 이동 | 같은 문서에서 라우터가 기록에 맞는 UI 구성 |
| Next.js 최초 접속·새로고침 | 서버가 준비한 HTML 표시와 Client Component hydration |
| Next.js App Router 내부 이동 | 라우터 캐시 또는 필요한 서버의 RSC 결과로 UI 갱신 |

### 전통적인 SSR과 bfcache

문서 단위로 이동하는 사이트에서 브라우저는 떠난 페이지를 bfcache에 보관할 수 있다. 적용되면 DOM과 JavaScript 실행 상태 등을 보존한 페이지를 복원하므로 서버에 매번 새 문서를 요청할 필요가 없다.

bfcache를 사용할 수 없으면 문서를 다시 로드하며 HTTP 캐시나 서버 응답을 이용할 수 있다. HTTP 캐시는 응답 자원을 재사용하는 기능이고, bfcache는 페이지의 실행 상태까지 복원한다는 차이가 있다. SSR이 뒤로 가기마다 항상 새 서버 렌더링을 뜻하는 것은 아니다. [web.dev: bfcache](https://web.dev/articles/bfcache)

### CSR SPA

라우터가 같은 문서 안에서 URL에 맞는 컴포넌트를 표시한다. 문서 전체가 새로 로드되지 않아도 라우트 변경으로 컴포넌트가 제거되면 해당 로컬 state는 사라질 수 있다. 계속 유지되는 컴포넌트의 상태는 유지될 수 있으므로 CSR이 항상 모든 컴포넌트를 제거하는 방식이라고 설명하지 않는다.

### Next.js와 Server Component

Next.js App Router는 최초 접속의 서버 렌더링과 이후 Link를 통한 클라이언트 전환을 함께 사용한다. 내부 이동과 기록 복귀에서는 사용 가능한 라우트 결과를 재사용하거나 필요한 RSC Payload를 서버에서 받아 UI를 갱신한다. 공유 Layout은 유지될 수 있다. [Next.js: Linking and Navigating](https://nextjs.org/docs/app/getting-started/linking-and-navigating)

Server Component의 소스 코드를 브라우저가 실행해 이전 화면을 만드는 것은 아니다. 서버에서 실행된 결과를 활용한다. 구체적인 캐시와 페이지 상태 보존 범위는 Next.js 버전과 설정에 따라 달라질 수 있다.

내부 이동에서 쓰는 라우터 캐시와 브라우저의 문서 복원 기능인 bfcache는 다른 계층의 기능이다. Next.js에서도 외부 사이트 등으로 문서 자체를 떠났다가 복귀하면 브라우저의 문서 복원 동작이 관여할 수 있다.

## 방문 기록과 상태 보존은 별개

기록에 `/products?page=3`이 남으면 해당 URL을 읽어 3페이지를 다시 구성할 수 있다. 로컬 state에만 저장한 입력 초안까지 자동으로 복원된다는 뜻은 아니다.

| 보존할 내용 | 고려할 방법 |
| --- | --- |
| 검색어·필터·페이지 번호 | URL에 표현하고 복귀 시 읽기 |
| 목록 데이터 | 데이터 캐시 또는 서버 재조회 |
| 작성 중인 입력 | 상위 상태, Store나 저장소 등에 보관 |
| 유지 중인 UI의 로컬 상태 | Layout 또는 Activity 등의 생명주기 확인 |
| 스크롤 위치 | 브라우저·라우터 복원과 목록 높이 변화 확인 |

Activity도 방문 기록을 관리하는 기능은 아니다. UI 상태를 유지하는 수단과 어느 URL로 돌아갈지 관리하는 수단을 구분한다.

## 말로 설명하기

브라우저 히스토리는 방문 기록 목록과 현재 위치로 이해할 수 있습니다. 뒤로 가기는 기록을 삭제하지 않고 현재 위치를 옮기므로 앞으로 가기가 가능하고, 뒤로 간 뒤 새 페이지로 이동하면 이후 기록을 버리고 새 기록을 추가합니다. SSR 문서 이동은 bfcache 복원이나 문서 재로드를 사용할 수 있고, CSR은 라우터가 같은 문서에서 화면을 바꿉니다. Next.js는 최초 HTML 렌더링과 이후 RSC 기반 클라이언트 전환을 함께 사용합니다. 기록이 남는 것과 모든 화면 상태가 보존되는 것은 별개입니다.
